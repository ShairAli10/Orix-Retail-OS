# Orix workflow contract

Scope: single-counter offline desktop. Preserve existing workflows while hardening touched capabilities.

| Capability        | Canonical owner                            | Contract                                                                           |
| ----------------- | ------------------------------------------ | ---------------------------------------------------------------------------------- |
| Settings sections | SettingsPanel in renderer/index.tsx        | Natural content height within existing main-content scroller                       |
| Buttons           | Global styles.css and native button        | Named actions, keyboard focus, busy/disabled states                                |
| Dialog            | components/dialog.tsx                      | Label, focus containment, Escape, focus restoration                                |
| Files             | Electron main-process dialog               | OS-owned save/open chooser; renderer cannot select an arbitrary export destination |
| Feedback          | Shared Toast plus inline role=status/alert | Important errors persist inline; no success on cancellation                        |
| Support           | features/support/diagnostics-panel.tsx     | Owner permission in backend; export is manual, no automatic transmission           |

Diagnostics: display loading, logging-unavailable, cancellation, success, and failure states. Prevent duplicate export submission. Recovery notices advise checking Sales History; never assert that every interrupted operation rolled back. Raw crash dumps stay local and are excluded from the support ZIP.

Existing untouched legacy dialogs and larger tables remain migration work; this contract does not certify all screens as compliant.

Onboarding: three named steps; automatic default location for the single counter; native form submission; focus first invalid input, including fields inside optional details. Setup secrets stay in memory. Post-setup readiness uses actual item/counter/backup status and explicitly labelled human confirmations. Persist only checklist booleans per owner in the local profile. Use a compact reminder on Sell to preserve checkout visibility.

Settings: five accessible tabs replace section shortcuts. Arrow keys and Home/End move between tabs; panels retain their state while hidden. Save and Discard appear only on Store & appearance and Receipts; the unsaved indicator remains visible throughout. Operational panels use the full content width. Appearance, store name and receipt edits remain drafts until Save Settings. Theme preview is restored to the saved preference on leaving Settings. Backup-folder updates preserve unrelated draft fields. Import, backup and user actions execute independently of Save Settings.

Inventory: default columns prioritize barcode, item, category, current/minimum stock, selling price, status and actions. Additional columns remain selectable with readable labels; item and action columns stay available. Item names are keyboard-operable detail buttons. Six summary cards keep cost and selling valuations separate; quantities across different units are not combined into a headline total. Wide tables scroll within their container, while filters reflow at narrower widths.

Reports: date edits remain drafts until Run Reports; Refresh reloads the applied dates. Validate missing or reversed dates before requesting data. Sales exports use the loaded report period; current-balance exports use the snapshot date. Ignore responses after their request is superseded or the page unmounts. Disable export and print while loading, unavailable or in an error state. Explain that sales and posted returns use the date range. Report tabs expose selection and support arrow/Home/End navigation; tables scroll within their container.

Sales History: invoice numbers open details by keyboard or pointer. Search/status controls have explicit labels; loading, failure and filtered-empty states are distinct. Superseded list requests cannot replace newer results. The details drawer reuses Dialog focus containment, Escape and focus restoration with its existing drawer layout; show sale date and returned quantities.

Sales Returns: preview and repository posting share the core refund allocation function, including original discounts/tax and cumulative partial-return rounding. Reject non-finite, negative or excessive quantities; require a selection and reason. A synchronous in-flight guard blocks repeated clicks, with fields and close actions disabled during posting. Backend validation remains authoritative, including cash already refunded. Posting failures stay inline; uncertain transport outcomes advise checking returned quantities. The return dialog uses shared keyboard focus and Escape handling.

Return accounting: preserve original invoices and expose separate none/partial/full return status, cumulative returned amount and net invoice total. Details show sold, returned and remaining quantities. Fully returned sales cannot start another return. Gross sales minus returns posted in the selected period gives net period sales, including returns of older invoices; invoice rows show cumulative returns. Cash returns reduce drawer cash; account credits reduce customer receivables. Only sellable returned quantities increase stock. No schema migration is needed for these derived summaries.

Sales list layout: five columns (invoice/customer, date, net sale total, one current status, View details). At 1100px and below, show sale cards. The list shows the invoice amount less cumulative returns, updating immediately after a return; full returns show zero. The original invoice amount, return breakdown and original payment remain in the details drawer. Status explains the invoice state. Reprint receipt and Return items live in the drawer; close it before opening their dialogs to avoid competing focus traps. Period reports continue to show net sales after returns.

Customer Book: default columns are name, phone, balance, status and actions; optional columns use readable labels and preserve name/actions. Balance sign is explained as To collect, Customer credit or Settled. At narrow widths, cards keep actions visible. Profile, edit and payment dialogs use shared focus handling; hide the profile while a child form is open to prevent competing focus traps. Remove unavailable WhatsApp placeholder.

Suppliers: five list columns (supplier, phone, balance, status, actions), with the same narrow-window cards as Customer Book. Explain payable balances as To pay, negative balances as Credit with supplier, and zero as Settled. Keep city, terms and last purchase in the profile. Supplier profile, edit and payment dialogs share focus handling; only one dialog is mounted at a time.

Buy Stock: six list columns keep purchase/supplier, date, original total, payment, status and available actions visible. Narrow windows use cards; item entry reflows into labelled columns. Draft, details and supplier-return dialogs share keyboard focus handling. Explain that saving a draft does not receive inventory. Supplier-return previews use the shared refund allocation including discounts and tax, excluding freight and other charges; validate quantities and require a reason. Preserve the original purchase total after returns.

Counter & Expenses: show cash differences as Cash shortage, Extra cash or Cash matches with an absolute amount. Require an explanation for a nonzero difference. Opening/closing fields freeze during submission; an immediate shared lock serializes refresh and mutations. Failed refreshes hide stale counter data. Closed sessions show Closing summary and disable expenses. Retain server-side expense idempotency, cash limits and closing validation.

Sell/POS: Held Sales uses the shared Dialog for focus containment and Escape. Resume verifies current product stock rather than relying on the initial catalog page, and confirms replacing a nonempty basket. Hold and Complete share an immediate request lock; interrupted Hold preserves the basket and advises checking Held Sales. At the supported 800px window width, checkout actions remain visible beside the basket; compact rows put item identity above quantity and price controls.

Stock workflow links: supplier profiles offer Buy from this supplier and preselect that supplier in a purchase draft. Items explain that creating a product does not add stock; Inventory distinguishes opening quantities, corrections and supplier deliveries. Purchase rows distinguish Draft — stock not added from Received — stock added. Received purchases link to the supplier account for balance and payment. Supplier payments are account-level, with no invoice allocation; do not display the unchanged purchase paid field as an unpaid invoice status. The focused purchase E2E verifies draft neutrality, receiving, returns, supplier payment, stock and cash effects through actual forms and IPC reads.

Supplier details: prioritize one current account balance with a settled/credit/owed explanation. Use Details, Transactions and Activity views; remove duplicated payment view and placeholder purchase view. Hide empty optional fields. Keep historical starting balance and business identifiers in an expandable section explaining that starting debt is already part of the account history.

Customer details follow the supplier panel: one current balance, Details/Transactions/Activity, notes within Details, and historical starting balance in expandable information. Transactions use five columns with plain-language debit/credit labels; hide internal source-ID references while retaining real document references. Negative running balances are explicitly customer credit.

POS customer lookup: components/search-select.tsx uses Downshift for a single searchable selection field. The chosen name (or Walk-in Customer) is the field value; typing shows matching options. Escape and blur restore the committed value without changing the customer. Stale responses are ignored, failed searches have inline retry, and unmatched searches show explicit feedback. Barcode + and Enter perform the same cart action; an empty barcode disables +, with an accessible Add scanned item name and tooltip.

Notifications: routine action success uses one shared bottom toast, owned by the initiating action. Settings state callbacks do not announce a second save when a backup folder changes. Do not repeat an inline error in a toast; checkout recovery errors remain visible inline until resolved.

SQL migration review: Settings owns the entry point and shared Dialog owns the full-width review overlay. A source SQL dump is read, never executed. Product review is paginated (25 rows), searchable and filterable; owner corrections are separate from original source values. Exclusion affects duplicate checks. Form errors block affected rows while warnings require acknowledgement, reset after edits. Drafts are local to the Electron profile and bound to a source-file SHA-256; choosing the same file resumes the saved draft. Only one modal is mounted while editing a product/contact. Pass one is explicitly review-only: no live import action is enabled until main-process backup, validation, atomic posting and reconciliation are implemented.

SQL import posting requires an owner-reviewed snapshot, explicit confirmation of opening quantities/history exclusions, and a fresh verified backup. Main-process validation is authoritative. Included products, contacts, opening movements, source mappings and the import audit commit together. Retrying the same SQL content returns its completed result; changed exports cannot repost mapped source IDs. Unsupported source rows must be excluded; negative stock must be corrected explicitly. Completed reports survive restart and can be downloaded from Data & backup. Imported contacts start with zero debt; historical transactions remain outside this import.

Fresh-import reset is an explicit owner action under Data & backup. It requires the owner password, exact typed confirmation and a closed counter. A verified backup must succeed before any deletions. Preserve users/settings/backups/audit history; clear trading records/import mappings atomically and clear cached baskets/review drafts before reloading. Never run this automatically when selecting or importing a SQL file.

Counter recovery: an owner may reopen an accidentally closed session on the current store-local date, with a required reason. Resume the same session/float and retain the previous closing snapshot in the audit log atomically. Do not duplicate opening cash or overwrite historical evidence. Reject non-owner, historical-day and stale closing requests. Clear the closing form after reopening so the next close requires a fresh cash count.

Reprinted sales receipts reflect retained quantities and net totals after returns, explicitly labelled as updated. Fully returned sales show no retained items and zero total. Original totals and cumulative returned/cash-refunded amounts remain visible in the receipt breakdown; original database invoices remain unchanged. Cash returns deduct from drawer cash through the existing ledger exactly once; credit returns reduce receivables without affecting cash.

Sales History date filters: default Today is the computer-local calendar date, from local midnight inclusive to next midnight exclusive, independently of the counter session. Yesterday, Last 7 days (including today), Custom range (inclusive dates), and All time combine with search/status and reset pagination. Native select/date controls follow the existing Reports convention; OS popup behavior is intentional. Invalid custom ranges display an inline correction and do not query all-time data. Filter state is transient in this single-window offline app. Relative ranges follow midnight while the page is open.
